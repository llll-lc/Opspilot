# 07 开发流程与跨会话协作

## 1. 目标

通过仓库事实、任务编号、测试和 Git 防止新会话重复操作、范围漂移和“提示词交接失真”。聊天快照只提供背景，不是项目状态的唯一事实源。

## 2. 信息权威顺序

发生冲突时按以下顺序判断：

1. 当前代码、迁移、自动化测试、实际环境和 Git 历史证明的事实。
2. 已确认且最新的 ADR 与专题规格。
3. `TASKS.md`、当前 `tasks/OP-xxx.md`、`CURRENT_STATE.md`。
4. `PROJECT_CONTEXT.md`。
5. 旧交接记录。
6. 聊天快照、临时建议和未确认想法。

规格与实现冲突时不能私下选一边：先判断是实现遗漏、文档过期还是正式需求变化，再在任务边界内处理。

## 3. 文档职责与去重

| 文件 | 唯一职责 | 不应包含 |
|---|---|---|
| `PROJECT_CONTEXT.md` | 长期目标、边界、关键决定 | 每日进度、命令输出 |
| `CURRENT_STATE.md` | 当前阶段、下一任务、阻塞 | 完整需求和历史日志 |
| `TASKS.md` | 唯一正式任务状态与依赖 | 实现细节和长篇交接 |
| `tasks/OP-xxx.md` | 单任务范围和验收；状态仅为非权威快照 | 其他任务实现、正式状态源 |
| `handoffs/OP-xxx.md` | 任务实际结果和证据 | 未来任务详细设计 |
| `docs/*.md` | 专题规格 | 重复任务状态 |
| `decisions/*.md` | 有争议的重要决策及理由 | 日常小选择 |
| Git | 文件变化和提交历史 | 需求讨论全文 |

不再建立重复的 `TASKS.yaml`、总决策流水账或按会话复制的长提示词。

## 4. 新会话启动流程

1. 完整读取 `AGENTS.md`、`PROJECT_CONTEXT.md`、`CURRENT_STATE.md`、`TASKS.md`。
2. 读取当前任务文件、直接引用规格、ADR 和前置任务交接。
3. 检查 `git status`、最近提交、目录、相关实现和环境状态。
4. 对照测试和任务表判断已完成、部分完成或文档过期，禁止重复造文件。
5. 运行轻量基线检查并记录已有失败。
6. 先报告冲突、用户现有改动和处理原则，再开始修改。
7. 只执行当前任务，结束时留下可验证状态。

## 5. 单任务生命周期

```text
TASKS: NOT_STARTED
→ 预检与冲突审计
→ TASKS: IN_PROGRESS
→ 实现与自测
→ 验收证据
→ 必要交接 + CURRENT_STATE + TASKS
→ git diff / 密钥 / 来源检查
→ 本地 Git 提交
→ TASKS: DONE
```

任务文件中的“状态快照”不作为权威状态。若真正需要用户输入或外部状态才能继续，写清唯一阻塞、已完成部分和恢复条件。

## 6. 防重复开发规则

- 新会话不能仅凭 `CURRENT_STATE.md` 或旧提示词判断是否完成；必须检查代码、测试和 Git。
- 创建文件、表、迁移、路由、工具、Prompt 或 Compose 服务前先使用文件/代码搜索。
- 若已有实现满足要求，补验证和文档，不重写同名替代版本。
- 若已有实现部分满足，只做最小增量并保留兼容性。
- 同一事实只有一个权威文档；其他文件使用链接，不整段复制。
- 交接只记录实际结果、命令和差异，不写下一会话可自行核验的猜测。

## 7. Git 规则

- OpsPilot 使用独立本地 Git 仓库，不纳入 `D:\Agent\BidPilot`、`learning_knowledge` 或 `models`。
- 每个 OP 任务原则上对应一个可审查的本地提交；必要时可拆分，主题必须包含任务 ID。
- 不自动 push，不创建远程仓库，不更改用户全局 Git 配置。
- 不使用 `git reset --hard`、强制覆盖或未经许可删除用户改动。
- 提交前检查 `git diff`、密钥、模型、大型数据、数据库卷和第三方资产。
- 工作区有无关改动时保护并绕开，不能假定由当前会话产生。

建议提交信息：

```text
docs(OP-000): establish OpsPilot specifications
feat(OP-003): add reproducible Superset fault lab
test(OP-009): add trajectory evaluation suite
```

## 8. 任务交接

出现代码、环境、架构或数据版本实质变化时创建 `handoffs/OP-xxx.md`；纯文档初始化可由提交和 `CURRENT_STATE.md` 作为证据，不强制另建空交接。

验收证据优先级：自动化测试结果、可复现命令、场景断言、数据库迁移、评测报告、资源记录、截图。聊天中的“完成了”不算证据。

## 9. 变更管理

范围外想法先登记到 `docs/09_RISKS_AND_CHANGES.md`：动机、证据、成本、影响任务和状态。未经项目所有者确认只能是 `PROPOSED`。

正式变更需要同步更新受影响的业务/架构/数据规格、ADR、`TASKS.md` 和长期上下文。技术实测导致的候选版本/部署回退可按 OP-001 授权执行，但仍要记录证据。

## 10. 用户必须参与的事项

尽量只保留：

- 在本地填写 API Key、密码或完成账号登录。
- 批准依赖、镜像和外部官方资料下载。
- 决定付费、远程仓库、公开发布和许可证风险。
- 对界面体验、演示效果和求职表述真实性做最终确认。
- 跟随复盘实际运行系统，保证能够解释关键设计与代码。

需求设计、编码、测试、合成数据、文档和一般本地操作由 Codex 在当前任务授权内完成。

## 11. 复盘要求

每个阶段交付面向学习者的短复盘：业务问题、数据流、Agent 知识、关键取舍、失败样本、运行方法和面试问答。复盘不重复逐行代码，也不能等最终才一次性补写。

## 12. 新会话提示词模板

```text
继续开发 D:\Agent\OpsPilot。先完整读取 AGENTS.md、PROJECT_CONTEXT.md、CURRENT_STATE.md、TASKS.md 和当前任务文件，检查 Git、实际实现、测试与环境。先报告规格和现实冲突以及已存在的能力。本会话只完成 OP-XXX，不提前实现其他任务；完成后按 AGENTS.md 留下验收证据和必要交接。
```

不需要把旧会话全部讨论或为每个新会话重新生成长提示词。
