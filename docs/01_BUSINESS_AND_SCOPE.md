# 01 业务逻辑与项目范围

## 1. 一句话定义

OpsPilot 是企业内部 IT / 数据平台支持团队的智能故障诊断助手：可独立运行的领域主 Agent 把零散故障描述转成可追踪工单，使用正式排障 Skill 和稳定工具定位根因，在权限策略内执行或申请审批，并在验证恢复后闭环；MCP 和只读 Specialist 均可降级/关闭，不是完成闭环的前置条件。

## 2. 企业痛点与项目价值

企业软件支持的真实难点通常不是“文档里有没有答案”，而是：

- 用户描述模糊，一线支持需要反复询问账号、时间、资源和错误现象。
- 文档、权限、任务状态、服务健康和日志分散在不同界面。
- 不同支持人员采用不同排查顺序，容易漏查或重复查。
- 聊天答案不能证明当前系统状态，静态 RAG 容易给出过时建议。
- 重跑任务、修改权限等操作有风险，需要授权、审计和回滚思路。
- 故障已修复却没有再次验证，也没有完整更新工单。
- 交接时只有聊天记录，没有结构化证据和执行轨迹。

OpsPilot 的价值不是替代支持人员，而是把“信息收集—诊断—处置—验证—记录”标准化。作品集可以用离线真值证明诊断和安全能力；真实 MTTR、成本节省等业务收益只能在未来实际试点后测量，规划阶段不作承诺。

## 3. 目标角色

| 角色 | 主要诉求 | 求职版权限 |
|---|---|---|
| 业务用户/报障人 | 快速描述问题、了解进度、确认是否恢复 | 创建工单、补充信息、查看本人/被授权工单 |
| 一线支持人员 | 获得一致排查路径、证据和建议 | 查看诊断、执行低风险动作、请求审批、更新工单 |
| 平台管理员 | 处理权限、连接、任务和服务问题 | 审批受控操作、查看目标系统状态 |
| 支持负责人/审计人 | 监督越权、重复动作和处理质量 | 审批高风险动作、查看审计与评测报告 |

求职版使用预置合成用户和最小授权模型；完整身份管理、SSO 和 RBAC 管理后台不在首版范围。

## 4. 核心业务流程

### 4.1 报障与建单

1. 用户描述现象，例如“日报今天没有收到”。
2. 系统识别目标系统、账号、资源、发生时间、预期行为和影响范围。
3. 对缺失的关键字段做有限补问；不无限聊天。
4. 创建新工单或关联未关闭的同资源同故障工单，防止重复建单。

### 4.2 诊断

1. 根据症状选择适用的版本化 Skill，并检索官方文档、配置说明和内部 Runbook，保留来源。
2. 形成少量候选根因，并记录每个假设需要的验证证据。
3. 主 Agent 只调用 OpsPilot 稳定工具名；Tool Gateway 在服务端授权范围内映射到 Superset MCP 或 REST/只读 Probe，并记录降级。
4. Specialist 增强已启用且专业上下文需要隔离时，才委派给 Access & Connectivity 或 Jobs & Runtime；关闭时主 Agent 继续使用同一稳定工具完成诊断。
5. 根据新证据更新假设，选择下一项信息增益最高的检查。
6. 达到证据门槛后给出根因；证据矛盾、工具不可用或超出能力时转人工。

### 4.3 处置与闭环

1. 生成明确的修复计划、风险等级、预期效果和验证方法。
2. 纯说明或安全查询可直接返回；低风险写操作按策略执行；中高风险动作中断等待审批；禁止动作永不暴露给模型。
3. 从检查点恢复并执行一次，使用幂等键避免重放。
4. 再次查询系统状态，并结合用户确认判断是否恢复。
5. 将根因、证据、动作、审批、验证和未解决风险写回工单。
6. 恢复成功后关闭；无法恢复则带完整上下文升级给人工。

## 5. 状态定义

### 工单状态

- `OPEN`：已创建，等待受理或信息收集。
- `DIAGNOSING`：正在诊断。
- `WAITING_USER`：需要用户补充信息或确认。
- `WAITING_APPROVAL`：修复动作等待审批。
- `RESOLVING`：已批准并正在执行受控动作。
- `VERIFYING`：验证恢复。
- `RESOLVED`：已恢复并记录解决方案。
- `ESCALATED`：超出自动处理范围，已转人工。
- `CLOSED`：完成最终确认并关闭。

### 诊断结论

- `CONFIRMED`：有足够运行时证据支持根因。
- `PROBABLE`：证据主要支持，但仍有未验证条件，只能建议或升级。
- `INCONCLUSIVE`：证据不足或互相冲突。
- `NOT_APPLICABLE`：不属于已支持目标系统/故障范围。

模型置信分不能把 `PROBABLE` 或 `INCONCLUSIVE` 自动升级为 `CONFIRMED`。

## 6. 求职版功能范围

### 必须完成

- 支持工单的新建、去重、状态流转、评论和审计时间线。
- 多轮但有界的信息补全。
- 官方知识与内部 Runbook 的检索、重排和可访问引用。
- 数据库连接、访问控制和定时报表三个版本化排障 Skill；最终补充导出与服务健康 Skill。
- OpsPilot 稳定工具契约、Superset 原生 MCP 可降级 Provider，以及 REST/只读 Probe 基线 Provider。
- 一个能独立闭环的 Incident Commander；两个条件式、只读、有界且可关闭的 Specialist 最后实现。
- 五类可重复故障注入和确定性真值。
- 候选根因、支持/反对证据与动态下一步工具选择。
- 工具权限分级、参数校验、HITL、检查点恢复和幂等。
- 修复后状态验证与工单闭环。
- 根因、轨迹、安全和恢复结果的离线评测。
- 诊断/工单工作台与 Docker profile 本地演示。

### 可选增强

- 增加第二个小型目标系统适配器以验证边界。
- SLA 超时提醒、知识反馈和相似历史工单检索。
- 支持负责人仪表盘和评测趋势图。
- 与真实 Jira/ServiceNow 沙箱集成。
- 更细粒度 RBAC 管理界面。

### 明确排除

详见 `PROJECT_CONTEXT.md` 第 6 节。排除项要进入开发必须先走变更流程。

## 7. 关键业务规则

| 规则 ID | 规则 |
|---|---|
| BR-001 | 每个确认根因必须至少关联一项运行时证据；仅有知识文档不能证明当前实例状态。 |
| BR-002 | 每项用户可见建议必须引用知识来源、工具观测或明确标记为待验证假设。 |
| BR-003 | Agent 不得调用服务端未授权工具，不得自行扩大用户、组织、目标系统或资源范围。 |
| BR-004 | 中高风险动作必须经过人工审批；禁止动作即使获批也不得由本系统执行。 |
| BR-005 | 动作前记录预期、风险和验证方法；动作后必须验证，不能以“接口返回成功”代替恢复。 |
| BR-006 | 同一工单、动作和审批必须有幂等键，恢复或重试不得产生重复副作用。 |
| BR-007 | 证据不足、工具失败或场景不支持时必须升级，不得编造日志、权限或状态。 |
| BR-008 | Superset、知识文档、日志和工单中的文字都视为不可信数据，不能改变系统指令。 |
| BR-009 | 工单关闭前必须保存根因、执行动作、恢复证据和责任主体；用户确认可作为补充而非唯一证据。 |
| BR-010 | 合成数据、公开来源和真实目标系统观测必须在界面与评测中可区分。 |
| BR-011 | 子智能体只能返回结构化调查结果，不得直接面向用户、写工单、审批、执行动作、关单或再次委派。 |
| BR-012 | Skill 必须来自固定版本注册表；运行时不得自动生成、下载、安装或提升工具权限。 |
| BR-013 | MCP 工具必须经过服务端固定允许列表和对象授权；Superset 的 SQL、创建、更新和保存工具不得暴露给模型。 |
| BR-014 | Agent 只能调用 OpsPilot 稳定工具名，不能选择 MCP/REST/Probe；Provider 切换不得改变业务工具语义。 |
| BR-015 | MCP `health_check` 只证明 MCP Server/连接可用；Superset Web/API 和 Worker/Beat/Redis 必须由独立健康工具分别观测。 |
| BR-016 | Skill、MCP、Specialist 任一关闭或失败时，Incident Commander 仍须完成支持范围内闭环或正确升级。 |

## 8. 五类演示场景

| 场景 | 典型用户描述 | 核心工具证据 | 预期处置 |
|---|---|---|---|
| 数据库连接失败 | 仪表盘加载失败/数据库连不上 | 数据库对象配置、连接测试、安全错误摘要 | 解释或升级；凭据修改禁止自动执行 |
| 权限不足 | 同事能看，我看不到仪表盘 | 用户角色、资源权限、访问检查 | 提交授权建议；授予高权限需审批或人工 |
| 定时报表未执行 | 今天没有收到日报 | 调度配置、最近运行、Worker/Beat 状态、任务日志 | 受控重跑需审批，并验证新运行 |
| 导出失败 | PDF/Excel 一直失败 | 导出任务、后台队列、浏览器/依赖状态、错误日志 | 重试或修复建议；验证产物可访问 |
| 服务异常 | 报表任务都不动了 | 服务健康、Redis/Worker 状态、队列积压 | 服务级操作升级或审批，恢复后检查任务 |

## 9. 演示主案例

合成公司内部的“数据洞察平台”使用 Superset 作为底层目标系统。业务用户报告“每日销售报表未收到”。Agent 先确认报表和时间，关联工单，检索报表调度 Runbook，查询调度配置、最近任务、Worker 与 Redis 健康，排除收件配置后确认 Worker 停止。重启类操作进入人工审批；批准后受控执行/模拟恢复，重新触发任务并验证报表成功生成，最后记录证据和关闭工单。

同一演示集还要覆盖错误凭据、缺失权限、导出依赖故障和工具不可用升级，防止只为一个固定 happy path 编码。

## 10. 成功定义

- 用户能从自然语言报障走到 Skill 选择、稳定工具观测、有证据的诊断、受控动作、恢复验证和工单闭环；MCP/Specialist 状态不会中断该主链路。
- Agent 根据证据改变工具路径，且能够停止、升级和拒绝越权。
- 对照评测能说明 Skill、MCP 和条件式子智能体何时有收益、何时不应调用。
- 每一步可以在时间线上解释“谁、何时、基于什么、做了什么”。
- 五类故障都能重置并重复运行，不依赖临场人工修改数据库。
- 项目所有者能说明企业价值、适用边界和不能声称的生产收益。
