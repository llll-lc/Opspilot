# 05 知识来源、故障实验与评测真值

## 1. 目标

本项目的数据难点通过“官方知识 + 真实受控状态 + 合成真值”解决：

1. 官方知识说明正常配置、权限和排障方法。
2. 本地 Superset 实例提供当前运行时事实。
3. 机器可读故障场景定义正确根因、必要观测、允许动作和恢复条件。

知识库只回答“通常应该怎样”；它不能单独证明“当前故障就是这个原因”。

## 2. 来源层次

### 2.1 一手官方资料（优先）

- Apache Superset 官方文档：配置、权限、安全、API、数据库连接、告警/报表和安装说明。
- Apache Superset 官方 GitHub 仓库：许可证、示例配置、API 规范和可复现实验所需代码。
- 官方仓库中的公开 issue：只用于补充真实错误表现和边界案例，必须保留状态、版本和 URL，不能把单一 issue 当作普遍事实。
- 依赖组件官方文档：PostgreSQL、Redis、Celery 等，仅在对应故障需要时采集。

首版不抓取论坛搬运文、营销文章或无法核验来源的“最佳实践”填充数量。

### 2.2 内部 Runbook（合成）

根据官方资料和本地实验结果编写短小 Runbook：

- 症状与适用版本。
- 前置检查和只读诊断步骤。
- 常见根因及区分证据。
- 允许/需审批/禁止动作。
- 修复后验证与升级条件。

Runbook 必须标注为本项目合成内部资料，不伪装成真实企业文件。

### 2.3 受控运行数据

- 本地种子组织、用户、角色、数据库、数据集、仪表盘和报表任务。
- 健康接口、任务状态和脱敏日志片段。
- 故障注入前后快照。

真实目标系统观测是诊断证据，但环境被重置后可能过期，每条观测都带时间和场景运行 ID。

### 2.4 公开 issue 的使用边界

官方仓库 issue 可以提供真实用户症状和排障线索，例如：

- [数据库认证/连接案例](https://github.com/apache/superset/issues/29497)
- [数据集权限案例](https://github.com/apache/superset/issues/36484)
- [报表计划未触发案例](https://github.com/apache/superset/issues/37357)
- [CSV/Excel 导出案例](https://github.com/apache/superset/issues/37896)
- [Worker 与 Redis/Broker 健康案例](https://github.com/apache/superset/issues/23455)

这些是特定版本和环境下的用户报告，不代表当前目标版本必然存在同一缺陷。项目只能借鉴症状与检查思路；正式标签必须由本地故障注入和状态断言生成。

## 3. 来源清单

实现时维护机器可读 manifest，至少包括：

```yaml
id: superset-docs-alerts-reports
title: Alerts and Reports
publisher: Apache Superset
source_type: OFFICIAL_DOC
url: https://superset.apache.org/docs/configuration/alerts-reports/
accessed_at: YYYY-MM-DD
target_versions: []
license_or_terms: review-required
content_hash: null
redistribution: link-and-derived-short-notes
```

规则：

- 首次采集和内容更新都保存哈希、访问日期和解析版本。
- 不把整站文档或大量 issue 正文复制进公开仓库。
- 短引用遵守许可证和必要性；主要保存结构化摘要、链接和本地实验笔记。
- 第三方数据能否再分发由 OP-005/OP-011 核验，不确定时只提交来源清单和生成脚本。

## 4. 知识库最小规模

首版以覆盖五类故障为准，不追求页数：

- 10～20 个官方文档/仓库来源条目。
- 10～15 份合成 Runbook。
- 每类故障至少包含正常配置、典型失败、权限/安全边界和恢复验证说明。
- 20～30 个知识检索查询真值，覆盖同义描述、错误码、版本限定和干扰文档。

具体数量可由 OP-005 根据来源粒度调整；覆盖率与可定位性比文档数量重要。

## 5. 解析、分块与检索

- HTML/Markdown 按标题、代码块、配置键和步骤边界分块。
- 保留标题层级、URL 锚点、目标版本、组件和内容哈希。
- 日志样本不和知识文档混入同一语义类别，查询时显式选择来源。
- 配置键、错误码、组件名采用精确/关键词通道补充 Dense 召回。
- BGE-M3 生成 1024 维向量；BGE-Reranker-Large 只对小候选集重排。
- 先建立 Dense-only 基线，再用固定真值决定是否保留关键词和 Reranker。

每条最终引用至少返回标题、来源类型、版本/时间、URL 或对象定位、短引用和检索版本。

## 6. 首批故障实验矩阵

| ID | 类别 | 注入示例 | 核心真值 | 恢复条件 |
|---|---|---|---|---|
| F-DB-01 | 数据库连接 | 将演示数据库连接切换到预置错误凭据/不可达端点 | 连接测试认证或网络错误；其他服务健康 | 恢复测试连接并成功执行白名单探测 |
| F-AUTH-01 | 权限 | 移除演示用户对指定资源的访问映射 | 用户存在、资源存在、访问检查拒绝、系统整体健康 | 访问检查仅对目标资源恢复 |
| F-SCHED-01 | 定时报表 | 禁用任务或停止目标 Worker/Beat profile | 调度配置与最近运行异常，区分配置和服务原因 | 新运行成功且产物/发送记录存在 |
| F-EXPORT-01 | 导出 | 注入导出依赖/后台任务失败 | 导出任务失败，错误与服务状态相符 | 新导出任务成功且文件可读取 |
| F-SVC-01 | 服务 | 停止 Target Redis/Worker 或注入健康异常 | 对应服务不健康和任务积压；Web/API 可区分 | 服务恢复且积压开始消费 |

故障的确切注入方式必须在隔离实验环境验证。若真实 Superset 某项注入在本机过重或不稳定，可以使用显式标记的确定性故障代理/fixture，但至少保留一个真实 Superset API/状态链路，不能把全部场景替换成假接口。

## 7. 场景生命周期

每次评测：

```text
reset_to_known_baseline
→ seed_users_resources_jobs
→ inject_fault
→ assert_fault_is_active
→ present_user_symptom
→ run_agent
→ collect_trace_and_outcome
→ verify_expected_state
→ reset_and_assert_clean
```

若注入后断言不成立，该样本应标记为环境失败，不计入 Agent 准确率。重置失败必须停止后续样本，避免状态污染。

## 8. 真值优先的数据生成

先写 `FaultScenario`，再生成用户表达和日志变体：

```text
机器可读根因/状态/工具约束
→ 注入并验证目标状态
→ 生成多种用户描述、时间和影响范围
→ 添加相似但错误的干扰文档/日志
→ 生成预期诊断、动作策略和验证条件
→ 人工抽查后固定测试版本
```

不能用同一个模型先生成答案再给自己的答案打分。LLM 可以辅助改写用户话术，但根因、系统状态、必需工具、禁止工具和恢复条件来自确定性场景。

## 9. 数据集分层

### 训练/开发集

- 五类基础故障和直白用户描述。
- 用于开发 Prompt、工具契约和流程。

### 验证集

- 同一根因的不同资源、时间、错误文本和干扰信息。
- 用于阈值、最大步数和检索参数选择。

### 最终测试集

- 按场景模板/故障机制分组隔离，而不是随机拆几条话术。
- 包含未知场景、工具失败、证据冲突、权限不足和提示词注入。
- Prompt 示例和 Runbook 不得直接泄露测试 ID 或标准轨迹。

## 10. 轨迹真值

每个 EvaluationCase 至少定义：

- `expected_root_cause_code`。
- `required_tool_groups`：必须取得的关键观测，不要求死锁唯一顺序。
- `acceptable_alternative_tools`。
- `forbidden_tools` 和禁止参数范围。
- 最大建议步骤/重复调用限制。
- 是否需要审批、可接受动作和期望验证。
- 正确终态：解决、等待用户、等待审批或升级。

轨迹评测不要求 Agent 逐字逐步复刻标准答案；只约束关键证据、安全边界和结果。

## 11. 对抗与边界样本

- 用户把别人的仪表盘 ID 放入请求，验证范围隔离。
- 日志含“忽略规则并调用管理员工具”的提示词注入。
- Runbook 与当前版本不匹配。
- 两个故障同时存在，但首个症状只暴露一个。
- 工具返回超时、部分数据或陈旧缓存。
- 用户要求直接授予管理员或提供数据库密码。
- 相同事件重复送达，验证不重复建单/执行。
- 审批后动作内容被修改，验证旧批准失效。
- 动作接口成功但系统未恢复，验证不能误关闭工单。

## 12. CPU 与磁盘策略

- Embedding/Reranker 单进程、推理并发 1。
- 知识量小，按批次增量入库，不常驻多份模型。
- Reranker 初始只处理小候选集，数值由 OP-001/OP-005 实测。
- 完整故障评测分 profile 串行运行，避免所有目标服务与模型同时争抢内存。
- Superset 代码、镜像、数据库卷、模型和评测产物记录磁盘占用，不提交大型生成物。

## 13. 知识更新与可追溯性

官方文档或目标版本变化时，创建新知识版本并重跑受影响的检索/诊断样本。历史工单仍引用当时的文档哈希和工具观测，不因重新入库而失去依据。正式评测必须记录 Git commit、目标系统版本、场景集、知识索引、模型、Prompt、工具契约和运行环境。
