# OP-003 交接：Superset MCP 风险闸门与故障真值

## 结果

- Gate A 三类五场景已完成：`F-DB-01`、`F-AUTH-01` 与 Beat/Redis/Worker 三个调度运行时根因；全部连续三次 `baseline → inject → active → recover → clean` 通过，证据在 `evidence/`。
- `F-AUTH-01` 的当前可复验证据是命名数据源 `OP003 Restricted`（`evidence/OP-003_API_FIXTURE_LIFECYCLE_2026-09-05.json`）：每轮 Gamma Reader 对 `GET /api/v1/database/2` 得到 `404`，`GET /api/v1/database/?q=(page_size:100)` 为 `200` 但结果过滤该名称。测试创建该命名资源、三轮完成后删除（`created_fixture: true`、`removed: true`），无残留。
- 固定 `apache/superset:6.1.0-dev` 原生 MCP 可启动、JWT 拒绝未认证/无效 token（401）、有效 token 成功、审计日志可观测；`health_check` 只记录 CONNECTOR，Web `/health` 为 APPLICATION，reports profile 的 Worker/Beat/Redis 为 RUNTIME。
- 原生只读安全闸门 **未通过**：目录共 24 个工具、哈希 `909d8f8619022707d06e10fdda39f39e880ca34e8d1b4e0413877ec7234dc975`，含 10 个创建/更新/SQL 等危险工具。不得称 MCP 已安全接入；OP-006 必须固定稳定工具白名单并使用 REST/只读 Probe 回退。
- 当前 MCP 报告为 `evidence/OP-003_MCP_GATE_2026-09-05.json`：受控超限测试将隔离 profile 的上限设为 1 token，并确认 MCP 容器环境值同为 1；只调用 `get_instance_info`，实际得到 200、416 B、`isError: false`，故原生大小限制执行是明确的 **FAIL**。带 `--require-size-rejection` 的验证器先写入该报告，随后以退出码 1 安全失败；极短客户端超时探针为明确的 **PASS**。这不是部分结论；大小限制与原生只读目录一起构成 OP-006 不得直接暴露原生 MCP 的依据。
